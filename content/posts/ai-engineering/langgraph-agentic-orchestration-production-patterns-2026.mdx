Architectural challenge and practical solution

Long-running, stateful agentic workflows require explicit control plane primitives: typed shared state, conditional routing, durable checkpoints, and human-in-the-loop (HITL) interrupts. LangGraph treats the workflow as an explicit graph, making these concerns first-class and inspectable. This article unpacks production patterns, trade-offs against TypeScript-native alternatives (Mastra), and concrete implementation steps to run LangGraph workflows in production — including Vercel/Next.js deployment considerations and example code for durable graphs, validation/retry loops, and interrupt/resume.

> [!NOTE]
> LangGraph is an orchestration/control-plane framework. It does not supply models, prompts, or tools — you own those. The graph formalizes routing, state, and checkpoints while leaving domain logic in separate modules.

Key production patterns (canonical)
- Typed shared state passed between nodes (strong typing enables validation & migration).
- Conditional edges for retry, escalation, and intent-based routing.
- Tool nodes that call deterministic services (SQL, search, HTTP APIs) with idempotent retries.
- Interrupt/resume nodes for manual review or external events.

Trade-off summary (short)
- LangGraph: production-grade for durable workflows, observable graphs, checkpointing, resume, and complex routing.
- Mastra: TypeScript-native, first-class Vercel/Next.js fit; faster path for Next.js edge and serverless TypeScript deployments.
- CrewAI: fast scaffolding with role patterns; Python-first; good for prototyping lighter workflows.
- OpenAI Agents SDK: simplest when OpenAI lock-in is acceptable.

Repository layout and separation of concerns
- graph.py: contains only the graph topology, typed state and routing rules.
- logic.py: contains domain logic, validators, SQL builders, and deterministic tool wrappers.
- handlers/: HTTP entrypoints and durable resume endpoints.
- migrations/: state schema migration scripts.

Concrete, reproducible implementation (Python, typed) — minimal LangGraph workflow
- Purpose: a durable SQL-report workflow that retries SQL generation on validation failures, persists state, and supports manual review.

1) graph.py (typed)
```python
from typing import TypedDict, Optional, Dict
from langgraph import Graph, Node, Edge  # hypothetical import names; replace per installed LangGraph API

class ReportState(TypedDict):
    query: str
    sql: Optional[str]
    attempts: int
    last_error: Optional[str]
    status: str

GRAPH_NAME: str = "sql_report_workflow"

def build_graph() -> Graph[ReportState]:
    graph = Graph[ReportState](name=GRAPH_NAME, initial_state=ReportState(
        query="",
        sql=None,
        attempts=0,
        last_error=None,
        status="pending",
    ))
    # Nodes
    schema_lookup = Node("schema_lookup")
    sql_generation = Node("sql_generation")
    sql_validation = Node("sql_validation")
    sql_execution = Node("sql_execution")
    business_summary = Node("business_summary")
    # Add nodes
    graph.add_nodes(schema_lookup, sql_generation, sql_validation, sql_execution, business_summary)

    # Edges with conditional routing (expressed as callables that accept state)
    def route_after_validation(state: ReportState) -> str:
        if state.get("last_error"):
            return "sql_generation" if state["attempts"] < 3 else "business_summary"
        return "sql_execution"

    def route_after_execution(state: ReportState) -> str:
        if state.get("last_error"):
            return "sql_generation" if state["attempts"] < 3 else "business_summary"
        return "business_summary"

    graph.add_edge(schema_lookup, sql_generation)
    graph.add_edge(sql_generation, sql_validation)
    graph.add_edge(sql_validation, sql_execution, condition=route_after_validation)
    graph.add_edge(sql_execution, business_summary, condition=route_after_execution)

    return graph
```

2) logic.py (typed)
```python
from typing import TypedDict, Optional
import re
import psycopg  # hypothetical typed Postgres client
from dataclasses import dataclass

class ReportState(TypedDict):
    query: str
    sql: Optional[str]
    attempts: int
    last_error: Optional[str]
    status: str

def generate_sql(query: str) -> str:
    # deterministic SQL scaffold from a validated prompt -> real implementations must
    # use sanitized template generation (avoid raw concatenation).
    sanitized = re.sub(r"[;]", "", query)
    return f"SELECT region, SUM(revenue) as total_revenue FROM sales WHERE description LIKE '%{sanitized}%' GROUP BY region;"

def validate_sql(sql: str) -> Optional[str]:
    # Basic static validation: disallow DROP/DELETE and enforce aggregation
    if re.search(r"\b(drop|delete|truncate)\b", sql, flags=re.IGNORECASE):
        return "non-idempotent SQL detected"
    if "GROUP BY" not in sql.upper():
        return "missing aggregation"
    return None

@dataclass
class DBClient:
    dsn: str

    def execute(self, sql: str) -> list[dict]:
        with psycopg.connect(self.dsn) as conn:
            with conn.cursor(row_factory=dict) as cur:
                cur.execute(sql)
                return list(cur.fetchall())

def run_sql_execution(state: ReportState, db: DBClient) -> ReportState:
    if not state.get("sql"):
        state["last_error"] = "no-sql"
        state["attempts"] = state.get("attempts", 0) + 1
        return state
    error = validate_sql(state["sql"])
    if error:
        state["last_error"] = error
        state["attempts"] = state.get("attempts", 0) + 1
        return state
    try:
        rows = db.execute(state["sql"])
        state["status"] = "completed"
        state["last_error"] = None
        state["attempts"] = 0
        # attach results as needed (omitted for brevity)
        return state
    except Exception as exc:
        state["last_error"] = str(exc)
        state["attempts"] = state.get("attempts", 0) + 1
        return state
```

> [!IMPORTANT]
> Keep the graph (routing) and domain logic separate. Tests should mock domain logic to validate routing and resume behaviors deterministically.

Durability and checkpoints
- Persist state to a transactional store (Postgres, DynamoDB) on every edge transition. The graph library should checkpoint state before executing side-effecting nodes.
- Idempotency: tool nodes must be idempotent or guarded by operation-idempotency tokens. Record operation IDs in state.

HITL interrupt pattern
- Add an "interrupt" node that emits an external event (e.g., create review ticket). The orchestrator pauses the workflow (status=paused) and exposes a resume HTTP endpoint that accepts reviewer decisions and updates state; the graph resumes from the checkpoint.

Resume endpoint (FastAPI typed example)
```python
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel
from typing import Literal
from uuid import UUID

app = FastAPI()

class ResumePayload(BaseModel):
    workflow_id: UUID
    reviewer_decision: Literal["approve", "reject"]
    notes: str | None = None

@app.post("/resume")
def resume_workflow(payload: ResumePayload):
    # Lookup persisted state and graph position (pseudo-API)
    state, current_node = load_checkpoint(payload.workflow_id)
    if current_node != "human_review":
        raise HTTPException(status_code=409, detail="workflow not paused at human_review")
    if payload.reviewer_decision == "approve":
        state["last_error"] = None
        state["status"] = "resumed"
    else:
        state["status"] = "escalated"
    persist_state(payload.workflow_id, state)
    # enqueue graph runner to continue
    enqueue_runner(payload.workflow_id)
    return {"ok": True}
```

Vercel / Next.js deployment considerations
- Finding: Mastra is TypeScript-native and wins for Vercel-first deployments with lower cold starts and edge compatibility.
- LangGraph is Python-first. Deploying to Vercel/Next.js requires one of:
  - Run LangGraph as a separate service (FastAPI/LangServe) behind an internal API gateway; Next.js acts as the front-end and proxies requests.
  - Containerize the LangGraph server (Docker) and deploy to a serverful platform (AWS Fargate, Fly.io) while keeping Next.js on Vercel.
  - Re-implement orchestration control-plane in TypeScript using Mastra if deep Vercel integration is a hard requirement.

Practical deployment patterns
- Pattern A: Hybrid (recommended when using Next.js front-end)
  - Deploy LangGraph as an autoscaling FastAPI service with durable state in RDS/DynamoDB.
  - Expose a small Next.js API route that forwards start/resume requests to the LangGraph service.
  - Use signed tokens for request authentication.
- Pattern B: TypeScript-first (recommended when Vercel edge matters)
  - Use Mastra for orchestration if you need serverless edge handlers and lower latency.
  - Keep LangGraph for heavy-duty back-office workflows requiring complex checkpointing.

Step-by-step reproducible checklist (LangGraph production rollout)
1. Design typed state models and store migrations.
2. Implement graph topology (graph.py) with clear edge conditions and max-attempt guards.
3. Implement domain logic (logic.py) with strong unit tests and deterministic tool wrappers.
4. Integrate durability: transactional checkpointing on every directed edge transition.
5. Implement resume/HITL endpoints and audit logs for each checkpoint.
6. Add observability: per-node execution timings, counters for retries, and trace IDs across nodes.
7. Load-test with representative LLM latency profiles; validate throughput, tail latency, and storage throughput.
8. Decide deployment surface: containerized LangGraph service vs TypeScript Mastra for Vercel-first needs.

Operational observability (must-have signals)
- Per-workflow: lifecycle state, current node, attempts, last_error, duration since start.
- Per-node: execution time distribution, failure rate, retry counts.
- Per-tool: success rate and idempotency violations.
- Alerting: saturating retry loops, stuck workflows (no progress > threshold), and failed checkpoints.

When to standardize on two frameworks
- Recommendation: Standardize LangGraph for durable, inspectable workflows and Mastra or CrewAI for rapid scaffolding and Vercel-native apps. Teams gain depth on two stacks and reduce cognitive load across projects.

Appendix: quick migration plan (Mastra -> LangGraph)
1. Audit workflows to identify long-running and retrying patterns.
2. Extract typed state and domain logic into portable packages.
3. Implement LangGraph graphs that mirror Mastra control flow; reuse logic modules.
4. Deploy LangGraph as an internal service; gradually shift workflow start points.
5. Decommission Mastra orchestration after parity and performance validation.
