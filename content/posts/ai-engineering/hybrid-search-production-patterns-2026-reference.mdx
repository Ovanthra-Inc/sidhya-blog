Problem statement: BM25 excels on exact-match tokens (SKUs, names, acronyms) while dense vector search captures paraphrase and semantics. Naïve score averaging fails because sparse and dense scores are incompatible across engines and scales. Reciprocal Rank Fusion (RRF) solves the incompatibility by operating on ranks, but production requires careful tuning: candidate depth, reranker budget, latency cost, and index-time context engineering.

Solution summary: Run a two-stage retrieval pipeline — fast hybrid retrieval (BM25 + ANN vectors) merged by RRF (k ≈ 60), then apply a cross-encoder reranker on the top-N candidates (N between 50–200) to produce the final top-K for LLM context. Add contextual chunking at index time, parent-document resolution at retrieval time, and access-control filtering. The following sections present architecture, benchmarks, concrete code, and reproducible deployment steps.

> [!NOTE]
> Reciprocal Rank Fusion (RRF) merges ranked lists using ranks only; it avoids normalizing heterogeneous score magnitudes and is robust to engine score drift. Use k=60 as a stable default; tune per-corpus.

Design principles (short)
- Fuse ranks, not scores. RRF prevents score-incompatibility.
- Keep hybrid retrieval as cheap front-line: BM25 (Elasticsearch/OpenSearch) + ANN (FAISS/ScaNN/Qdrant).
- Shift precision work to cross-encoder reranker: compute-intensive but applied to narrow set.
- Index-time contextualization: store parent doc ids and context tokens to allow rehydration.
- Respect access controls at retrieval time — treat ACLs as filters, not post-hoc redaction.

Metric definitions and measurement:
- Retrieval Latency: time from query normalization to candidate list available.
- Reranker Latency: time to score top-N candidates and return top-K.
- Throughput: sustainable QPS under production load with typical batching.
- Memory: working set on a single node for the service component.

RRF implementation: formula and typed reference
Reciprocal Rank Fusion score for a document d over M ranked lists:

RRF(d) = sum_{i=1..M} 1 / (k + rank_i(d))

Where k is the RRF constant (recommended k=60). The algorithm uses rank positions; missing items count as infinite rank (contribute 0).

Practical TypeScript implementation (production-ready, typed)

- This code assumes you have two ranked arrays: bm25Hits and vectorHits, each is an array of { id, score } where score is ignored by RRF — only position matters. It returns a fused ranked list ready for reranking.

```typescript
// src/hybrid/rrf.ts
export type Hit = { id: string; score?: number; metadata?: Record<string, unknown> };

export interface RrfOptions {
  k?: number; // RRF constant
  maxResults?: number;
}

/**
 * fuseRanksRRF
 * Merge multiple ranked lists using Reciprocal Rank Fusion.
 */
export function fuseRanksRRF(lists: Hit[][], options: RrfOptions = {}): Hit[] {
  const { k = 60, maxResults = 200 } = options;

  const scoreMap = new Map<string, number>();
  const seenMeta = new Map<string, Hit>();

  for (const list of lists) {
    for (let i = 0; i < list.length; i++) {
      const position = i + 1; // ranks are 1-based
      const hit = list[i];
      const prev = scoreMap.get(hit.id) ?? 0;
      const contribution = 1 / (k + position);
      scoreMap.set(hit.id, prev + contribution);
      if (!seenMeta.has(hit.id)) {
        seenMeta.set(hit.id, hit);
      }
    }
  }

  const fused = Array.from(scoreMap.entries())
    .map(([id, score]) => ({ id, score, metadata: seenMeta.get(id)?.metadata }))
    .sort((a, b) => b.score - a.score)
    .slice(0, maxResults);

  return fused;
}
```

> [!TIP]
> Persist the original rank positions (bm25_rank, vector_rank) in candidate metadata to allow deterministic reranker features and easier diagnostics.

Operational recipe: reproducible implementation steps
1. Indexing & chunking
   - Chunk documents at 100–400 tokens; keep parent_id and parent_size metadata.
   - Apply contextual retrieval prep: create a 1–3 sentence "chunk context" via a small LLM that summarizes the chunk's parent section; store with the chunk.

2. Indexing engines
   - BM25: Elasticsearch/OpenSearch with English analyzer, store term vectors and enable search-time synonyms.
   - Vectors: FAISS HNSW (for on-prem) or Qdrant/Weaviate for managed with payload filtering.
   - Sync indexing pipeline to write both sparse and dense indexes atomically or via idempotent jobs.

3. Query path
   - Normalize query: lowercasing, spells, expand acronyms via dictionary, optionally HyDE (generate pseudo-queries).
   - Retrieve top 100 from BM25 and top 100 from vector DB concurrently.
   - Fuse candidate lists with RRF (k=60), keep top 200 candidates.

4. Reranking
   - Send fused top-100/200 to cross-encoder reranker.
   - Use batch size tuned to GPU (commonly 8–32), mixed precision (fp16), and asynchronous queueing with backpressure.
   - Return top-K (5–10) to prompt assembly.

5. Prompting & generation
   - Rehydrate parent documents for the final top-K.
   - Compress duplicate sentences and annotate citations with source ids and ranks.
   - Optionally run a self-reflective check: ask the LLM to rate confidence; if below threshold, trigger requery with expanded context.

6. Telemetry & evaluation
   - Track retrieval recall@100, NDCG@10 before and after reranking.
   - Measure end-to-end p50/p95 latency and cost per query (GPU-vs-CPU).
   - Maintain labeled dev/test holdouts and run nightly evaluation.

Operational checks and tuning knobs
- RRF k: 40–80 usually stable; lower k increases sensitivity to top ranks.
- Candidate depth: 100–200 recommended for domain content; increase for low-recall domains.
- Reranker model: compare vendor rerankers (Voyage rerank-2.5 claims +7.9% vs Cohere v3.5 in vendor-stated tests) with open-source cross-encoders (distilled bi-encoders + small cross-encoder fine-tune). Always run your own NDCG tests.

Empirical notes from 2026 field data
- A hybrid + rerank architecture reduces "lost in the middle" failures. Median retrieval latency increases modestly (≈+5–10ms) vs single-engine retrieval but NDCG improves significantly.
- Contextual chunking plus BM25 provides an additional 0.05 NDCG lift vs BM25 alone on name-heavy corpora (WANDS results).
- Large reranker context windows (Voyage's 32K support) reduce the need for aggressive chunk compression when parent documents are necessary.

Diagnostic checklist for production incidents
- If recall@100 drops: verify index freshness and vector/index shard health.
- If reranker latency spikes: check batching discipline and GPU memory fragmentation, and ensure mixed precision enabled.
- If hallucinations persist: increase reranker depth and add a citation-enforcement pass that penalizes unsupported claims.

Validation matrix: when to prefer which component

| Failure Mode | Action |
|---|---|
| Exact SKU/name misses | Increase BM25 boosts, add name-specific analyzers, or use phrase boosting |
| Paraphrase misses | Use denser embeddings; retrain on domain paraphrases |
| Reranker cost too high | Reduce top-N, switch to a distilled reranker, or use vendor-managed rerank endpoints |
| Access control leaks | Enforce ACL filtering at retrieval time; audit logs for retrievals |

Closing operational tips
- Run small, representative A/B tests comparing RRF k values and reranker depths. Report NDCG@10, latency, and cost-per-query.
- Keep reranker models under CI with a fixed evaluation set. Deploy model updates behind feature flags and gradual rollout.
- Instrument candidate metadata (bm25_rank, vector_rank, fused_score) to analyze failure modes offline.

> Use ranked-list persistence (store the top-100 fused output with timestamps) for faster debugging and rerun of reranker experiments without re-querying the indexes.
