Architectural challenge: agentic workflows invoke external tools via LLM-driven function calls. The performance bottleneck is the model's token-level decoding and decision tree over optional parameters in function schemas, which inflates time-to-first-token (TTFT) and time-between-tokens (TBT). This guide gives an engineering-first, production-ready approach to minimize tool-calling latency through schema hardening, constrained decoding, token-budget pruning, and GPU-aware batching.

Key insights summarized
- Remove redundant natural language in parameter descriptions and use concise, imperative names.
- Replace optional fields with multiple narrow functions that have required parameters.
- Use enums for finite-string parameters to shrink decoding branching.
- Prefer structured/constrained decoding (OpenAI-style structured outputs, vLLM masked generation) where possible — it reduces application retries and overall workflow latency despite a small CPU/GPU overhead.
- Reduce input tokens (context) and output tokens (response) with compact representations where policy allows.

> [!NOTE]
> This article focuses on production patterns. Validate any policy or privacy constraints (GDPR, PII) with semantic Pass-2 checks after schema validation — schema correctness ≠ policy compliance.

Design principles and measurable effects
- Decision-space reduction: converting N optional fields into M narrow functions reduces exponential decoding branches.
- Token efficiency: small input and compact outputs reduce attention and cross-attention compute.
- Constrained decoding: masks invalid tokens, preventing syntactic errors and reducing application-layer retries.

Practical benchmarks (controlled lab)
- Hardware: 1x A100 40GB GPU, vLLM server, batch-size=1, 8k context.
- Dataset: 10k agentic tool calls with mixed optional-heavy and hardened schemas.
- Measurement: median tool-call latency (end-to-end including vLLM generation + parsing), memory overhead (inference engine additional memory for constrained decoding), throughput (calls/sec).

Concrete optimization checklist
1. Audit current function schemas and optional parameters.
2. Convert broad tools with many optional fields into several specialized tools with required fields.
3. Replace free-text string fields with enums where values are finite and known.
4. Shorten descriptions to imperative labels, and keep schema metadata minimal.
5. Reduce input context: move historical logs to embeddings store and only supply top-K documents.
6. Use structured/constrained decoding when supported — pass strict JSON schema to inference engine.
7. Implement a lightweight application-layer semantic validator separate from schema validation.
8. Measure TTFT, TBT, and 95th percentile latency before/after changes.

Typed TypeScript: generator for hardened function schemas and enum extraction
```typescript
// schema-generator.ts
import fs from "fs";

type ParamType = "string" | "integer" | "boolean" | "enum";

export interface ParamSpec {
  name: string;
  type: ParamType;
  description?: string;
  enumValues?: string[];
  required?: boolean;
}

export interface FunctionSpec {
  name: string;
  description?: string;
  params: ParamSpec[];
}

/**
 * Build a tight JSON Schema for function-calling / structured output APIs.
 * - Removes long descriptions
 * - Converts optional-heavy params into required where applicable
 * - Enforces enums for finite strings
 */
export function buildTightJsonSchema(func: FunctionSpec): Record<string, unknown> {
  const properties: Record<string, unknown> = {};
  const required: string[] = [];

  for (const p of func.params) {
    const prop: Record<string, unknown> = {};
    if (p.type === "enum" && p.enumValues) {
      prop.type = "string";
      prop.enum = p.enumValues;
    } else {
      prop.type = p.type === "integer" ? "integer" : p.type === "boolean" ? "boolean" : "string";
    }
    // Keep descriptions short and imperative if present
    if (p.description) {
      prop.description = p.description.split(".")[0]; // truncate to first sentence
    }
    properties[p.name] = prop;
    if (p.required) required.push(p.name);
  }

  return {
    type: "object",
    properties,
    required,
    additionalProperties: false
  };
}

// Example usage
const example: FunctionSpec = {
  name: "create_incident",
  description: "Create a new incident with severity and owner.",
  params: [
    { name: "title", type: "string", description: "Short incident title", required: true },
    { name: "severity", type: "enum", enumValues: ["P1", "P2", "P3"], description: "Severity level", required: true },
    { name: "owner_id", type: "string", description: "Owner user ID", required: true },
    { name: "notes", type: "string", description: "Optional notes", required: false }
  ]
};

const schema = buildTightJsonSchema(example);
fs.writeFileSync("create_incident.schema.json", JSON.stringify(schema, null, 2));
```

> [!TIP]
> When generating schemas programmatically, enforce additionalProperties=false to make constrained decoding strict and predictable.

Typed Python: minimal inference wrapper using vLLM with constrained decoding (OpenAI-compatible)
```python
# vllm_inference.py
from typing import Dict, Any, List, Optional
import json
import requests

class VLLMClient:
    def __init__(self, base_url: str, api_key: Optional[str] = None) -> None:
        self.base_url = base_url.rstrip("/")
        self.headers = {"Authorization": f"Bearer {api_key}"} if api_key else {}

    def call_with_schema(self, model: str, messages: List[Dict[str, str]], json_schema: Dict[str, Any], max_tokens: int = 256) -> Dict[str, Any]:
        """
        Calls an OpenAI-compatible vLLM server using structured output / constrained decoding.
        Assumes the server supports `response_format` with a JSON schema.
        """
        payload = {
            "model": model,
            "messages": messages,
            "response_format": {"type": "json_schema", "json_schema": json_schema},
            "max_tokens": max_tokens,
            "stream": False
        }
        resp = requests.post(f"{self.base_url}/v1/chat/completions", headers=self.headers, json=payload, timeout=30.0)
        resp.raise_for_status()
        data = resp.json()
        # Provider returns content in choices[0].message.content (structured)
        content = data["choices"][0]["message"]["content"]
        # If the provider already returns parsed JSON, this is a no-op. Otherwise parse text.
        if isinstance(content, dict):
            return content
        return json.loads(content)

# Usage
if __name__ == "__main__":
    client = VLLMClient("https://vllm.example.internal", api_key="REDACTED")
    messages = [{"role": "system", "content": "You are a compact function caller. Respond only with the JSON object."},
                {"role": "user", "content": "Create incident with title 'DB outage', severity P1, owner 1234."}]
    with open("create_incident.schema.json", "r") as f:
        schema = json.load(f)
    result = client.call_with_schema(model="llama-3b", messages=messages, json_schema=schema)
    print(result)
```

Implementation steps (reproducible)
1. Inventory: export all function schemas used by your agents and count optional fields per function.
2. Categorize: tag functions with >5 optional fields as "wide" (candidates for refactor).
3. Refactor: split "wide" functions into focused functions with required args. Example: split update_user(all) -> update_user_email, update_user_role.
4. Enum extraction: gather values for string fields and convert to enums in schema files. Use frequency thresholds to decide enums vs open string.
5. Shorten descriptions: replace long natural language with 3–5 token imperative labels (e.g., "Owner user ID" -> "owner_id").
6. Pass schemas to inference engine: if using vLLM or compatible provider, pass JSON schema via response_format; enable constrained decoding.
7. Reduce context: move logs/large objects to an embedding store; supply only top-k IDs + short descriptors.
8. Measure baseline and delta: TTFT, TBT, median and p95 latency, throughput, and memory impact.
9. Add semantic validator: run policy checks (entitlements, GDPR) on the parsed object before external tool invocation.
10. Rollout: Canary the hardened schemas with 1% traffic, monitor error rates and latency; incrementally roll out.

Edge cases and fallbacks
- If the model fails constrained decoding due to model mismatch or tokeniser differences, implement a deterministic parser fallback that validates and transforms model output server-side, then return a structured error to the LLM for a regenerated response.
- Avoid over-constraining when values are legitimately open-ended (free text). Use hybrid patterns: enums for most calls, free text for exceptional fields.

Operational monitoring
- Instrument every tool call with: schema_name, schema_version, tokens_sent, tokens_received, TTFT, TBT, decode_errors, semantic_validation_time.
- Create SLOs for median tool-call latency and error budget for decode errors.
- Alert on rising decode_errors or semantic validation failures (could indicate schema drift).

Further considerations
- Tokeniser behavior: JSON with repeated keys expands tokens; compact binary-ish encodings (messagepack-like patterns or positional compact formats) can reduce token count but increase parsing complexity and policy review. Use only where latency critical and security-reviewed.
- GPU/Memory: constrained decoding increases GPU memory and compute by holding token masks and automata. Profile for your model size and batch patterns.
- Security: ensure schema-driven calls do not leak sensitive configuration in prompts. Keep prompts minimal and authorize tool calls server-side.

Final note
Optimizing tool-calling latency is a cross-stack engineering task: schema design, prompt/token budget, constrained decoding, and hardware profiling must be treated together. Tight schemas and enums deliver the largest predictable wins; compact input and constrained decoding add measurable reductions in end-to-end latency at acceptable memory cost for production deployments.
